# JWT Security Notes

## JWT Attacks

- JWTs are commonly used in **authentication, session management, and access control**
- Vulnerabilities can potentially **compromise the entire website**

---

## What is a JWT?

- Standardized format for sending **cryptographically signed JSON data** between systems
- Most commonly used to send **user claims** (identity, roles, permissions)
- All data stored **client-side** within the token itself — unlike classic session tokens
- Popular in distributed systems where users interact with **multiple back-end servers**

---

## JWT Structure

```
header.payload.signature
```

All 3 parts are separated by dots. Header and payload are **Base64URL-encoded JSON**.

- **Header** — metadata about the token (algorithm used, key ID, etc.)
- **Payload** — the actual claims about the user
- **Signature** — verifies the token hasn't been tampered with

### Example Decoded Payload

```json
{
  "iss": "portswigger",
  "exp": 1648037164,
  "name": "Carlos Montoya",
  "sub": "carlos",
  "role": "blog_author",
  "email": "carlos@carlos-montoya.net",
  "iat": 1516239022
}
```

> ⚠️ Header and payload can be **read and modified by anyone** with access to the token — security depends entirely on the signature.
> 

---

## JWT Signature

- Generated by the server by **hashing the header + payload** using a secret signing key
- Changing **even one byte** of the header or payload invalidates the signature
- Without the secret key, you **cannot generate a valid signature**

```bash
### Visual Flow
```
Header (JSON)  →  Base64URL  ─┐
                               ├→  HMAC-SHA256(secret key)  →  Signature
Payload (JSON) →  Base64URL  ─┘
```

## JWT vs JWS vs JWE

| Term | What it is |
| --- | --- |
| **JWT** | Base format — defines claims as JSON |
| **JWS** | JWT + **signature** — what people usually mean by "JWT" |
| **JWE** | JWT + **encryption** — contents are encrypted, not just encoded |

---

## What are JWT Attacks?

- Attacker sends **modified JWTs** to the server
- Goal: **bypass authentication / access controls** by impersonating another user

---

## Impact

- **Privilege escalation** — modify your own role/permissions in the payload
- **Account takeover** — impersonate any authenticated user
- Full compromise if attacker can **forge valid tokens**

---

## Why Do These Vulnerabilities Arise?

- JWT specs are **flexible by design** — leave many implementation details to developers
- Most common flaw: **signature not properly verified**
- If the **secret signing key is leaked, guessed, or brute-forced** → attacker can forge any token
- Even battle-hardened libraries can be misconfigured
